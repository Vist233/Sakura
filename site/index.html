Why Sakura

Coding agents are moving inside software.

Not only a tool a person opens, but a part another program runs.

  1. Parallel explorationSeveral agents try different approaches at once.
  2. Independent reviewA working agent forks a read-only reviewer.
  3. Local and remoteThe same agent works here or on another machine.

The problem is not intelligence.

It is how your software organises and controls the agent. There are three ways to get one.

Adopt an agent product

Fast to start.

Your software adapts to its interaction, tools, state and lifecycle.

Build from model APIs

Full control.

You rebuild the loop, tool protocol, context, sessions, errors and recovery.

Build with Sakura

A complete agent. Replace only what you need.

Model, sessions, tools, environment and policy each have their own boundary.

Define only the difference.

Developers should define what makes an agent different, not rebuild what every agent needs.

A branch reviewer, built in Infinity.

  
A working agent forks a reviewer that keeps the whole history but only reads. The reviewer sends advice back; the main agent decides.

  
  
Scheduling, structured results, advice delivery and the reviewer's lifecycle are Infinity's code. Sakura provides the session fork, assembly, plugins and the execution boundary. A tool the reviewer's model can still see is not a tool it may run: the guard checks every call before it runs.
